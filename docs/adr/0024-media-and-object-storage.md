# ADR 0024: Files go through the media service into S3-compatible storage; Garage is the bundled store

**Status:** Accepted (2026-10-27). Amends [0020](0020-pluggable-backends.md) (object storage implementations) and [0023](0023-osi-bundled-backends-and-wide-column-choice.md) (bundled backends).

## Context
Phase 4 adds file and image attachments. The plan reserves a `media` service (presigned S3, scanning, thumbnails, CDN) and an S3 contract for object storage ([0020](0020-pluggable-backends.md) listed MinIO as the bundled-style implementation).

MinIO's community edition no longer works as a bundled backend. Pre-built binaries and container images stopped in October 2025, the project went into maintenance mode in December 2025, and the repository was archived in February 2026. The code is still AGPL-3.0, but nothing is released.

Small and Medium installs need an object store that is OSI-licensed ([0023](0023-osi-bundled-backends-and-wide-column-choice.md)), small enough for one VM, and maintained.

## Decision

### The bundled store: Garage
**Garage** (AGPL-3.0, Rust) is bundled in the Small tier: one node, one copy (`replication_factor = 1`), SQLite metadata. Its secrets (RPC secret, admin token) and the media service's access key are generated by `install.sh` into `.env`. `xmsg-media garage-init` runs at every start as a one-shot job and creates, only if missing, the one-node layout, the access key and the bucket, through Garage's admin API (v2).

Any S3-compatible store still works through the contract: Ceph RGW, Amazon S3, GCS in S3 mode, or SeaweedFS. Its operator creates the bucket and key, and `garage-init` is skipped. Medium and Large point the media service at their store; the Helm chart's media deployment is a follow-up.

### Files go through the media service
Browsers upload to and download from `xmsg-media` (`/media/` behind the proxy), never from the store:
- **Every download checks membership** of the file's channel (`members_by_channel`), with the same 404 for "no such file" and "not a member".
- **The store stays private** (`127.0.0.1` / the internal network), so no CORS, no public bucket and no signed-URL leakage.
- **Nothing served can run as our origin.** Only images whose bytes we decoded (PNG, JPEG, GIF, WebP) are served inline, with their sniffed type. Everything else is `application/octet-stream` with `Content-Disposition: attachment`. Every response has `X-Content-Type-Options: nosniff` and `Content-Security-Policy: default-src 'none'; sandbox`. SVG is never inline.
- **Bounded memory:** uploads are limited to 25 MB (`XMSG_MEDIA_MAX_BYTES`) and handled at most 4 at a time (`XMSG_MEDIA_CONCURRENT_UPLOADS`). Image decoding is capped (12,000 px per side, 192 MB).

Presigned URLs and a CDN are for the Large tier, where serving bytes through our pods costs too much. They'll be added there with short-lived URLs and the same membership check at signing time.

### Metadata and thumbnails
- **Metadata:** one row per upload in Cassandra (`files`, keyed by `file_id`), written after the objects, so a row never points at a missing object. File IDs are time-ordered with 22 random bits, so they can't be guessed from a neighbour's.
- **Thumbnails:** made at upload, 400 px on the longest side, JPEG (PNG when the image has transparency). Stored next to the original.

### Not in this version
- **Virus scanning:** ClamAV needs 1.5–3 GB of memory and signature updates (a mirror for air-gapped installs). It's an optional profile for later, with files held as pending until scanned.
- **Deleting files** with their message, retention, and per-workspace quotas.
- **Resumable or multipart uploads** beyond 25 MB.
- **Files in thread replies** (top-level messages only for now; replies would need an `attachments` column on `thread_messages`).

### Files in messages
- **The client sends only file IDs** (at most 10). The messages service looks them up and writes each file's name, type, size and image size into the event, replacing anything the client put there.
- **Only your own uploads, in the same channel.** A file the sender didn't upload, or one from another channel, is refused like an unknown one.
- **Storage:** the sequencer copies the details into `MessageCreated`, the persister stores them in the `messages.attachments` blob, and history rebuilds them. A deleted message's attachments disappear with its body (the objects stay for now; see "Deleting files" above).

## Consequences
- The Small tier gains a backend: Garage (~50–100 MB of memory; capped at 256 MB) and two volumes (`garage-meta`, `garage-data`), which `xmsgctl backup` includes.
- The media service holds up to about 100 MB of uploads in memory at once, so it gets a 512 MB cap.
- Every file download costs a Cassandra read (membership), as history pages already do.
- Garage's admin API is part of the bootstrap. A Garage upgrade that changes it needs `garage-init` updated, which CI catches (it runs `garage-init` against the bundled version).

## Alternatives considered
- **SeaweedFS** (Apache-2.0): a broader S3 feature set, but more processes and memory for a one-VM install. Still usable through the contract.
- **A MinIO fork** (e.g. one that republishes binaries): a single-vendor fork with an uncertain future.
- **Local disk in the media service for Small:** no new backend, but two storage code paths, and the S3 contract untested in the most common install.
- **Presigned URLs everywhere:** less load on our service, but the store must be public (through Caddy with matching signatures and CORS), and a signed link works for anyone holding it until it expires.
